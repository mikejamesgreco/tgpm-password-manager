What is TGPM?
TGPM is a local-first password vault designed for everyday password storage. Your encrypted vault is a .tgpm file. Your independent 256-bit Recovery Key is a .tgpmkey file. You need both the Recovery Key and your Master Password to unlock the vault.
Encryption Architecture — Envelope Encryption with Key Wrapping

TGPM uses an envelope-encryption design with key wrapping. Your Master Password does not directly encrypt every credential in the vault. Instead, TGPM separates the key that protects the vault data from the key material used to unlock that key.

TGPM key hierarchy
1. Your Master Password is processed with PBKDF2-HMAC-SHA-256.
2. That password-derived material is combined with your independent 256-bit Recovery Key using HKDF-SHA-256.
3. The result is a Key Encryption Key (KEK).
4. The KEK protects, or “wraps,” a separately generated random 256-bit Data Encryption Key (DEK) using AES-256-GCM.
5. The DEK encrypts the TGPM credential payload using AES-256-GCM.

This pattern is commonly described as Envelope Encryption with Key Wrapping. KEK, DEK, and key wrapping are standard cryptographic/key-management terms. OWASP guidance discusses envelope-encryption/key-protection patterns, and NIST uses the terms Key Encryption Key and key wrapping in its key-management terminology.

TGPM follows these general architectural concepts in a local-first browser implementation. This wording does not mean TGPM is OWASP- or NIST-certified, approved, or independently audited.

Browser Environment & Extensions

TGPM runs inside your browser, so the security of the browser environment matters after a vault is unlocked. A browser extension that has permission to read or modify the TGPM page may be able to observe sensitive information displayed or entered in that page.

TGPM cannot reliably enumerate, verify, or temporarily disable all browser extensions. Browser extension management is controlled by the browser, not by ordinary page JavaScript. TGPM therefore cannot guarantee that an unlocked vault is isolated from extensions installed in the current browser profile.

For higher-security use, consider opening TGPM in a private-browsing window such as Microsoft Edge InPrivate or Google Chrome Incognito and make sure extensions are not permitted to run there. Private browsing by itself is not a security sandbox: an extension that you have explicitly allowed in private browsing may still run and interact with pages according to its permissions.

If you use TGPM in a normal browser window, review the extensions installed in that browser profile and their site/file access permissions. Proceed only when you trust the browser, device, and extensions that can access the TGPM page.

Microsoft Edge: Extension settings can control whether an extension is allowed in InPrivate and whether it can access local file: URLs. If TGPM is opened directly from its local HTML file, the extension's local-file access setting is particularly relevant.

Recommended higher-security workflow:
1. Open a fresh InPrivate/Incognito window.
2. Confirm that unneeded extensions are not permitted in that mode.
3. Open TGPM and unlock the vault.
4. Lock TGPM when finished and close the private window.

TGPM does not claim that private browsing prevents malware, a compromised browser, operating-system monitoring, screen capture, keylogging, or extensions explicitly permitted to run in that private session.
Recommended backup pattern
Keep the encrypted vault wherever convenient. Keep multiple Recovery Key backups, but preferably not only beside the vault in the same location. Losing either the password or every copy of the Recovery Key makes the vault unrecoverable.
Recovery Key Rotation — TGPM

In simple terms
Think of your Recovery Key as one of the two keys needed to open your TGPM safe. The other key is your Master Password. If you think someone may have obtained a copy of your Recovery Key, TGPM lets you replace it without changing your Master Password or rebuilding your password vault.

TGPM creates a brand-new Recovery Key, asks you to save it, and then makes you select the saved file again to prove that you really have a usable backup. Only after that verification does TGPM update the vault to require the new Recovery Key.

You might rotate your Recovery Key if, for example, a USB drive containing it was lost, the key file was accidentally shared or uploaded somewhere you do not trust, an old backup location may have been exposed, or you simply want to retire an older Recovery Key.

After rotation, keep multiple backups of the new Recovery Key in safe locations separate from the encrypted vault. The old Recovery Key will no longer open the newly saved vault.

Technical details
TGPM does not use the Recovery Key directly as the key that encrypts all of your credentials. Your credential payload is protected by a separate random 256-bit DEK (Data Encryption Key). The Master Password and Recovery Key are used together to derive a KEK (Key Encryption Key), and that KEK encrypts, or “wraps,” the DEK.

During Recovery Key rotation, TGPM first authenticates the current Master Password together with the current Recovery Key by deriving the existing KEK and successfully unwrapping the existing DEK. TGPM then generates a new independent 256-bit Recovery Key, requires verification of the saved .tgpmkey file, generates fresh PBKDF2 and HKDF salts, and derives a new KEK from the same Master Password + new Recovery Key.

The existing DEK is then re-wrapped with that new KEK. The encrypted credential payload itself does not need to be decrypted and re-encrypted merely because the Recovery Key changed. This separation is one of the reasons TGPM uses a DEK/KEK design.

Important historical-backup warning
Rotation changes the security of the updated vault; it cannot reach backward in time and revoke old copies. If you still have a pre-rotation backup of the .tgpm vault, that older vault can still be unlocked using the old Recovery Key and the Master Password that applied to that older copy. If rotation was performed because the old key may have been exposed, review whether old vault backups should also be securely removed.
Security History and Review Guidance — TGPM

Why TGPM tracks these dates
The dates are intended to help you understand the security history of your vault and remember to review your backups. TGPM does not treat a Master Password or Recovery Key as unsafe simply because it is old, and it does not force periodic changes on a fixed calendar.

Master Password
TGPM shows when your Master Password was last changed. Change it when you believe it may have been exposed, reused somewhere unsafe, or is no longer strong enough for your needs. A one-year age reminder is informational only and does not mean the password has expired.

Recovery Key
TGPM shows when your Recovery Key was last rotated. Rotate it if the key may have been copied, lost, shared, exposed, or stored somewhere you no longer trust. If more than a year has passed, TGPM suggests reviewing whether your Recovery Key backups still exist and are stored securely; rotation is not required solely because of age.

Privacy of this metadata
These timestamps are stored inside the encrypted TGPM-DATA payload rather than in the visible outer .tgpm metadata. Someone who only obtains the encrypted vault file should not be able to see when you last changed your Master Password or Recovery Key without first unlocking the vault.

Older vaults
Vaults created before v0016 did not record these dates. When such a vault is first opened in v0016, TGPM initializes the missing dates using the vault creation date as the best available historical baseline.
Security Validation & Testing

TGPM includes defensive and cryptographic regression tests intended to detect implementation errors as the application evolves. These tests cover different parts of the security boundary and should be interpreted separately.

Malformed File / Fail-Closed Testing (v0015)
TGPM was tested with intentionally damaged and structurally invalid vault and Recovery Key files. The test set included invalid JSON, incorrect TGPM format identifiers, unsupported versions, missing cryptographic metadata, invalid PBKDF2 iteration values, malformed Base64URL, incorrect IV sizes, missing ciphertext, and invalid Recovery Key lengths.

Testing verified that malformed or unsupported files are rejected before normal use, malformed vaults are distinguished from malformed Recovery Keys, and structurally valid files containing an incorrect Master Password or Recovery Key fail during cryptographic authentication rather than being misclassified as malformed. A valid vault with the correct secrets continued to unlock normally after the negative tests.

This testing demonstrates TGPM's fail-closed file handling: questionable input is rejected instead of being guessed at, repaired, reinterpreted, or partially loaded. It does not by itself prove that the cryptographic implementation is correct.

Cryptographic Regression / Known-Answer Testing (v0016)
TGPM's Crypto Self-Test uses a deterministic synthetic test vector in which the Master Password, Recovery Key, PBKDF2 salt, HKDF salt, AES-GCM IVs, DEK, ciphertext, and expected plaintext are all predetermined. Because every input is known, TGPM can compare its intermediate and final results against exact expected values.

The browser self-test verifies the complete TGPM v1 cryptographic chain: PBKDF2-HMAC-SHA-256 password derivation, HKDF-SHA-256 KEK derivation using TGPM-KEK-v1, AES-256-GCM DEK unwrapping, AES-256-GCM vault decryption, and validation of the resulting TGPM-DATA structure.

The same synthetic vector was also successfully verified with an independent Python implementation using the cryptography library. Agreement between TGPM's Web Crypto implementation and an independent implementation provides useful regression and interoperability evidence and helps detect accidental cryptographic implementation drift.

What these tests do not prove
Passing these tests does not constitute an independent professional security audit, prove that every TGPM source-code path is free of defects, or establish that the browser, operating system, device, clipboard environment, or other software on the computer is secure. The tests provide specific evidence about malformed-input handling and the consistency of TGPM's implemented cryptographic chain; they are not an absolute software-security guarantee.
Security Review — TGPM

The Security Review button runs TGPM's reusable one-click security regression suite intended to be carried forward with every release. It includes the deterministic cryptographic known-answer self-test, runtime security invariants, locked-state checks, and live inspection of TGPM's executable inline JavaScript and document structure.

The review checks security invariants such as Web Crypto availability, expected PBKDF2/HKDF/AES-GCM configuration, the deterministic cryptographic known-answer test, the single-source application version design, auto-lock configuration, locked-state controls, and whether credential rows remain in the DOM after locking.

The source inspection monitors for unexpected network APIs, external runtime resources, dynamic code execution such as eval or the Function constructor, dynamic script creation, browser storage APIs, clipboard reads, document.write, JavaScript URLs, workers, messaging APIs, and changes to approved DOM-writing patterns such as innerHTML. Expected/approved uses are tracked separately so that a new occurrence can be reported as security drift rather than silently accepted.

The review also carries explicit security expectations. Future versions compare monitored source counts and security assumptions against those expectations so ordinary release changes cannot silently redefine what is considered normal.

Results are classified as PASS, INFO, WARN, or FAIL. Source findings include source line numbers when a monitored pattern is present, making the review immediately actionable. Copy Review Text copies the complete report, including locations, as plain text for review or comparison between releases. A PASS means the tested invariant matched TGPM's current security expectations; it is not a professional vulnerability assessment or proof that the application is free of security defects. WARN and FAIL findings should be reviewed before treating a new version as trusted.
Cryptographic Self-Test — Included in Security Review

What it verifies
The self-test checks the complete TGPM v1 cryptographic chain against a fixed known-answer vector: PBKDF2-HMAC-SHA-256 at 600,000 iterations, HKDF-SHA-256 KEK derivation using TGPM-KEK-v1, AES-256-GCM DEK unwrapping, AES-256-GCM vault decryption, and validation of the resulting TGPM-DATA structure.

Why deterministic vectors matter
Normal TGPM vaults intentionally use fresh random salts, IVs, Recovery Keys, and DEKs, so two legitimate vaults will not produce identical ciphertext. A regression vector fixes those inputs on purpose so future TGPM versions can prove that the same inputs still produce and decrypt the same expected cryptographic results.

Independent verification
The companion v0016 test suite includes the same vector in JSON plus a Python verifier using the independent cryptography library. Passing both the browser self-test and the external verifier helps detect accidental implementation drift between TGPM's Web Crypto implementation and an independent implementation.

Important
The embedded vector contains only public synthetic test secrets. It is not a real vault and must never be reused for actual credentials.
Malformed File Protection — TGPM

What TGPM checks before opening a vault
TGPM verifies the outer JSON structure, format and supported version, PBKDF2/HKDF/AES-GCM algorithm metadata, PBKDF2 iteration range, Base64URL encoding, salt and IV sizes, wrapped-DEK ciphertext presence, and encrypted payload presence before attempting normal unlock processing.

Recovery Key validation
A Recovery Key file must identify itself as TGPM-RECOVERY-KEY, use the supported version, contain valid Base64URL, and decode to exactly 256 bits. Invalid key files are rejected separately from incorrect-but-valid credentials.

After decryption
TGPM also checks that decrypted content is a supported TGPM-DATA object with an entries array and structurally valid entry/security metadata before loading it into the application.

Fail closed
If a file is malformed or unsupported, TGPM does not try to guess, repair, reinterpret, or partially load it. The file is rejected and no vault state is changed. A structurally valid vault that simply cannot be authenticated produces a separate unlock-failed message for an incorrect Master Password, Recovery Key, or authenticated ciphertext.

This validation is defensive application hardening. It does not replace AES-GCM authentication or the cryptographic protections already used by TGPM.
Clipboard Protection — TGPM

TGPM accesses the clipboard only in response to an explicit user action. Clicking Copy writes the selected password to the clipboard. Clicking Clear Clipboard asks TGPM to overwrite the current clipboard value with an empty value.

TGPM does not read or inspect your clipboard and does not perform delayed background clipboard access. TGPM therefore does not intentionally request broad clipboard-read permission merely to implement automatic cleanup.

Recommended Windows cleanup:
1. When you are finished using a copied password, click Clear Clipboard in TGPM.
2. If Windows Clipboard History is enabled, press Win+V and choose Clear all to remove retained clipboard-history entries as well.

Clearing the current clipboard does not necessarily erase copies retained by Windows Clipboard History, cloud clipboard synchronization, virtual-machine software, remote-desktop software, clipboard managers, or other applications. TGPM cannot control those external histories, so clipboard cleanup is an explicit user-managed security step.
Master Password Security — TGPM

Password change: TGPM requires the new Master Password to differ from the current Master Password; re-entering the same password is rejected.
TGPM now enforces a Master Password policy when creating a vault and when changing the Master Password.

Minimum length: 15 characters.
Maximum length: 128 characters; TGPM does not silently truncate it.
Characters: Spaces, symbols, mixed case, and Unicode are allowed. TGPM does not require arbitrary uppercase/lowercase/number/symbol composition rules.
Weak-password screening: Common passwords and obvious predictable patterns are rejected locally, including examples such as password, simple sequences, repeated characters, and predictable variations of common passwords.
Privacy: This screening happens entirely inside TGPM. Your Master Password is not sent to an Internet password-checking service.
Passphrases: Long memorable passphrases are supported and encouraged.

This policy follows the direction of current NIST/OWASP password guidance: favor sufficient length and block known/predictable choices rather than forcing traditional composition rules. TGPM uses a 15-character minimum because a stolen local vault presents an offline-guessing threat and TGPM deliberately chooses the stronger non-MFA password-length baseline.

TGPM also applies PBKDF2-HMAC-SHA-256 with 600,000 iterations before combining the password-derived material with the independent Recovery Key. The Recovery Key remains a separate randomly generated 256-bit secret.
Where TGPM's cryptography comes from

TGPM does not implement its own versions of AES, SHA, PBKDF2, or HKDF. The cryptographic operations are performed by the browser's standard Web Crypto API through window.crypto and crypto.subtle.

The browser supplies cryptographically strong random values and the low-level key-derivation, encryption, and decryption primitives. TGPM defines how those established building blocks are combined into its two-secret vault architecture.

What you are responsible for

For everyday use, choose a strong Master Password you can remember, keep the Recovery Key separate from the encrypted vault, and maintain independent backups. If you lose the required secrets, TGPM has no backdoor or password-reset service.

Also protect the computer and browser while the vault is unlocked. Encryption at rest cannot protect a password that malware or another person can read from an already-unlocked vault.
How TGPM protects your passwords — Simple explanation

TGPM creates a strong random encryption key for your vault. You never have to remember or manage this internal key yourself.

To unlock that encryption key, TGPM requires two independent things: your master password (something you know) and your separately stored TGPM Recovery Key (something you have). Neither one can unlock the vault by itself.

Your master password can therefore be something you can reasonably remember, while the Recovery Key supplies a large, randomly generated secret that is extremely difficult to guess.
How TGPM protects your passwords — Technical explanation

TGPM generates a random 256-bit Data Encryption Key (DEK). The DEK encrypts the credential payload using AES-256-GCM.

Your master password is processed with PBKDF2-HMAC-SHA-256. TGPM combines that password-derived material with the independent 256-bit Recovery Key using HKDF-SHA-256. The result is a Key Encryption Key (KEK). The KEK encrypts, or wraps, the DEK using AES-256-GCM.

In short: password + Recovery Key → KEK → unlocks DEK → decrypts credentials.
Changing your Master Password — Simple explanation

Your master password does not directly encrypt every password stored in your vault. TGPM has a separate strong random key that does that job.

Your master password and Recovery Key work together to protect that internal vault key. When you change your master password, TGPM only needs to protect the same internal vault key with your new password. Your Recovery Key stays the same, and your entire credential vault does not have to be rebuilt or re-encrypted.

Think of it like changing the combination on a secure box that contains the key to another locked room. The room and everything in it stay exactly where they are; only the way you gain access to its key changes.
Changing your Master Password — Technical explanation

The credential payload is encrypted by the random 256-bit DEK. The DEK is separately wrapped by the KEK derived from the master password and Recovery Key.

When the master password changes, TGPM first derives the old KEK from the old password + existing Recovery Key and unwraps the DEK. It then generates fresh derivation salts, derives a new KEK from the new password + same Recovery Key, and re-wraps the same DEK with AES-256-GCM.

Because the DEK itself has not changed, the encrypted credential payload does not need to be re-encrypted. Changing the master password and rotating the Recovery Key are therefore separate security operations.
Security assurance
TGPM is designed for everyday password storage using standard browser cryptographic primitives and a deliberately separated Master Password + Recovery Key design. Its built-in regression suite validates cryptographic known-answer behavior, fail-closed input handling, source-security invariants, and locked-state cleanup. TGPM has not yet undergone an independent third-party security audit, so no absolute software-security guarantee is made.
